Abstract

This study asks which content pages should receive limited review time first. I built a monthly client-content modeling frame from the FlyRank Search Intelligence warehouse, using February 2026 as the feature window and March 2026 as the outcome window, with client-level holdout validation to prevent pages from the same client appearing in both training and test data. The target marks pages whose March impressions declined by at least 20% relative to February, and models were compared with a transparent baseline using Precision@50. The baseline and Random Forest both achieved 0.280 Precision@50, while Logistic Regression reached 0.220 and Decision Tree 0.120, so the tested learned models did not improve on the baseline. The result supports a cautious decision-support workflow: keep the simple baseline as the default benchmark, use model scores as an experimental challenger, apply a minimum-visibility guardrail, and require human review before any content action.

1. Introduction / Problem statement

A content or SEO team rarely has enough time to inspect every page. The operational decision is therefore not “is this page good or bad?” but which pages deserve attention first. The project is framed as a ranking/scoring task that creates a short review queue for a human reviewer.

The intended action is to inspect high-priority pages and then choose an appropriate response — refresh, expand, protect, prune, or monitor — based on the evidence available for that page. A false positive wastes limited reviewer time; a false negative risks overlooking a page that may deserve attention.

Primary metric: Precision@50, because the decision is explicitly about the quality of the first 50 rows in the review queue.

2. Data

The project uses the full FlyRank ML Internship warehouse release available through Hugging Face. The daily performance warehouse contains 78,835,655 rows, spanning 2025-01-27 to 2026-06-30, with 427,292 observed client-content pairs.

February 1–28, 2026

7,355,108 daily rows across 28 dates. Only information available by the February 28 cutoff is eligible as model input.

Outcome window

March 1–31, 2026

9,841,378 daily rows across 31 dates. March is reserved for the observed outcome and excluded from honest feature inputs.

Across February and March combined, 17,196,486 daily rows were observed. GSC data was available for 6,232,844 rows, GA4 data for 559,287 rows, and both sources for 489,027 rows. Missing source availability is not treated as genuine zero activity.

Public-safe rule: no client names, domains, URLs, private queries, credentials, or raw exports are published. Pseudonymous identifiers are used internally for grouping and joins only.

3. Methodology

Unit of analysis and label

One modeling row represents one client_hash_id × content_hash_id pair observed in both February and March. After joining the two windows, the modeling frame contained 303,572 rows. The binary target is declined_20pct: 1 when March impressions are at least 20% lower than February impressions, otherwise 0. The positive rate is 12.6% (38,131 positive rows).

Features

The model uses seven decision-time features: February impressions, clicks, sessions, average-position signal, word count, character count, and content age in days. Missing content features are median-imputed rather than dropping large parts of the population.

Baseline and models

The baseline is a transparent score based on February visibility and position. Three learned comparators are trained: Logistic Regression, Decision Tree, and Random Forest.

Validation design

A client-level holdout split is used. Training contains 264,134 rows from 40 clients; testing contains 39,438 rows from 10 clients; client overlap is 0. The test positive-label rate is 9.5%, compared with 13.0% in training, showing that client composition materially changes the evaluation setting.

Leakage control

March outcome fields are not included in model scoring. The feature window ends before the outcome window begins, and client identifiers are excluded from the predictive feature matrix. This makes the evaluation a future-window decision-support test rather than a reconstruction of the label from future information.

5. Limitations & honest framing

  • The result is tied to one February→March window and one client-holdout split; it is not a multi-window backtest.
  • The 20% impression-decline label is a decision proxy. It does not explain why performance changed.
  • The current feature set is intentionally small and omits many potentially useful search and content signals.
  • Random Forest ties rather than beats the baseline, so it should not be presented as a superior production ranking system.
  • The test label rate differs from training (9.5% vs 13.0%), which indicates client heterogeneity and makes repeated grouped validation a valuable next step.
  • Feature importance, model scores, and observed associations are not causal evidence.
  • No claim is made that changing or refreshing a flagged page will improve rankings, traffic, or engagement.

6. Ranked recommendations

The capstone produces a review queue, not an automated content-action engine. During inspection, the raw model queue was dominated by extremely low-volume pages, so a practical guardrail of at least 100 February impressions was applied before generating the final review list. This threshold is operational, not universal.

After the visibility guardrail, 76,837 pages were eligible and the top 50 were retained for human review. Public outputs do not expose their pseudonymous identifiers.

Default operating recommendation

USE Keep the transparent baseline as the default ordering because no learned model improved Precision@50 on the held-out test clients.

Experimental challenger

TEST Retain Random Forest scores as a challenger for future grouped/time-forward evaluations, not as proof of superiority.

Action playbook

  1. Review first: inspect high-priority, sufficiently visible pages before low-volume pages.
  2. Investigate evidence: check impressions, clicks, position, content age, and available content context.
  3. Choose a human action: refresh, expand, protect, prune, or monitor only after review.
  4. Do not auto-rewrite: a score orders attention; it does not establish causality or prescribe an edit.
  5. Re-evaluate: repeat the experiment across additional months and clients before changing the default ranking policy.

9. Conclusion

This experiment turned a broad “which pages need attention?” question into a reproducible ranking evaluation with a future outcome window, leakage controls, a client-level holdout, a transparent baseline, and multiple learned comparators. The strongest learned model, Random Forest, matched but did not beat the baseline at Precision@50. That negative result is useful: it argues for keeping the simple method as the current default, tightening the ranking guardrails, and spending the next iteration on better features and repeated time-aware validation rather than deploying a more complex model without measured benefit.
